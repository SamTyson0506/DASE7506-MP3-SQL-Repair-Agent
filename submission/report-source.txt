1. Feedback-driven repair loop

Perceive, propose, check, submit

<b>1.</b> Check the exact original SQL. This produces an error or a concrete example comparison and satisfies the required ordering before hints. <b>2.</b> Read the shared repair_hint suggestions and deduplicate them by normalized SQL. <b>3.</b> Check the first distinct hint if its normalized query has not already been checked. Prefer a matching hint, then a matching original; any such choice can still undergo the checked refinements below.

<b>4.</b> If no checked SQL matches, request schema and rank remaining raw hints together with generic AST repairs. <b>5.</b> Check candidates in deterministic order. Each new observation determines which proposals remain eligible. Matching candidates may be refined using output metadata, unambiguous name binding, foreign-key paths, bag/count semantics and unused-join simplification; each changed SQL needs its own successful check. <b>6.</b> Submit a checked match, or an executable hint/draft fallback if no match is found. A fallback is not claimed to be correct.

Candidate operators

Operator family | Purpose

Schema and joins | Resolve columns and small spelling differences; connect missing relations by breadth-first search over declared foreign keys; try declared join keys.

Projection | Align the SELECT list with public example column metadata, including order and standard aggregates. No expected result rows are inserted as SQL answers.

Bag/set and counts | Toggle DISTINCT; try COUNT(*); group by output columns; remove unused joins or try an appropriate direct relation scan.

Comparisons | Case normalization, numeric text comparisons, partial categorical labels, and SQLite-compatible quantified comparisons.

Relational semantics | Try INTERSECT for two-value "both" predicates and EXCEPT for negated relationships; recover simple frequency/grouping queries.

Post-check refinement | Bind explicitly named entities to their own name fields; repair missing bridge relations; check conservative bag and unused-join alternatives.

Ordering | Try aggregation for grouped superlatives and, at low priority, a reversed ordering.

Selection, context and memory

Ranking uses fixed rule priorities, hint order and actual feedback such as row count. Canonical SQL identities prevent retrying equivalent generated candidates. A bounded 4,096-entry cache stores only syntax-normalization strings, never answers or database feedback. The authoritative task memory is its history; each task gets a fresh agent. There is no persistent answer memory, retrieval index, deployed learned model or network service.

The retrieve tool is intentionally unused. Schema-disjoint splits make direct training-SQL reuse risky, and retrieval would spend one of the eight calls. The final design spends those calls on checking SQL and schema repairs. Changing source prompts does not regenerate course hints.

The deployed workflow is assisted by the fixed LLM hint cache, with no live LLM planner. Generic post-check refinements align public column metadata, repair missing bridge tables, normalize hidden frequency counts and try preserving bag semantics for joined entity-name projections. Every changed SQL is checked before selection.

3. Reliability and safeguards

Observed failure modes

<b>Example collisions.</b> Multiple SQL queries can return the same public rows, especially empty results, while differing on extra instances. The checker provides evidence, not a proof of semantic correctness. Validation shows that trusting the original whenever it passes is particularly unreliable.

<b>Join multiplicity and grouping.</b> DISTINCT, COUNT(column), COUNT(*), and grouping by an identifier versus a name can agree on one instance and disagree on duplicated or null data. Fixed hints and local edits do not always select the correct multiplicity. Join trimming can also remove a relationship needed by the question.

<b>Long or misleading drafts.</b> Repetitive joins, nested subqueries, hallucinated columns and correlated aliases can exceed what four or five remaining check calls can repair. Local schema reassignment can damage a correlated reference. The implementation falls back transparently instead of inventing successful feedback.

<b>Language and annotation ambiguity.</b> Some training examples request a column or ordering in natural language that differs from the reference projection/order. Public column metadata helps, but it cannot recover every missing condition or resolve every ambiguous entity relationship. No task-specific reference queries were embedded to compensate.

Prompt-injection threat model

Task questions, cached hints, retrieved text, schema names and tool results are untrusted data. They could contain requests to ignore rules, open files, send data, execute code or change scoring. There is no instruction-following model at runtime; questions are consumed only by a few regular expressions. SQL is parsed as SQLGlot ASTs. Metadata-derived projection expressions are limited to identifiers and standard aggregates, excluding literals, subqueries and arbitrary expressions.

The implementation does not eval/exec tool content, run a shell, import generated code, read database paths, fetch URLs or modify traces. Only fixed action dictionaries reach official tools. Official read-only SQL validation, table/function allowlists, byte limits, time/resource bounds and scorer replay remain in force. Candidate SQL is accepted only after real checking when a match is available. A malicious hint can still reduce accuracy or consume budget; it cannot legitimately grant new permissions or supply forged tool observations.

4. Provenance and development experiments

Data boundaries

Training questions, SQL and permitted training-memory references informed generic rule development. Validation inputs, feedback and official validation outcomes guided design selection. Final test inputs were processed by the frozen candidate implementations through official tools; complete official evaluation was repeated to measure public-benchmark progress. No task-specific test labels, grading fingerprints or extra grading databases were read by the agent, converted into answers, or used as learned features. No database files or grading references are redistributed in this source export.

Training-derived controller priors

A training-only audit found 43 non-explicit-distinct cases where hints used a column count in ORDER BY or HAVING; 38 corresponding references used only COUNT(*). This motivated a checked normalization of hidden frequency counts, excluding explicit distinctness requests and LEFT JOIN queries. In 15 training cases with DISTINCT, joins, plain name projections and no grouping or explicit uniqueness/both request, 13 references preserved bag semantics. This motivated a checked name-bag candidate. These are generic structural conditions, not stored task IDs or answer SQL.

Broader bag/set classifiers were also fitted using training labels only. They did not improve the selected conservative name-projection policy and are not loaded or included as runtime assets. No validation/test rows were used to fit those classifiers.

A supervised LoRA trial used only 480 training examples: official training-memory gold SQL, schema and real original-draft checking feedback plus the fixed hints.
